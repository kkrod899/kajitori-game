# 実証実験 v1 契約 — アプリ化前でも中身は本番想定

Date: 2026-09-05
Status: Draft for production-scope validation
Branch: `experiment/production-scope-v1`

## 1. 前提

このフェーズは「簡易MVPを作る」フェーズではない。

**アプリとしての仕上げだけを省略し、家庭運営の内容・判断ロジック・網羅性・検証方法は本番想定で作る。**

MVPとして削ってよいのは、クラウド同期、アカウント、通知基盤、ストア配信、課金、複数端末同期、管理画面などのアプリ基盤である。

以下は削らない。

- 家庭運営項目の網羅性
- 家族構成・月齢・園利用などの適用条件
- 項目の出現条件
- 時間帯・期限・状態による優先順位
- 完了条件
- `気づく → 判断 → 実行 → 閉じる`の責任ループ
- 健康・安全項目の根拠
- 不要項目を抑制する仕組み
- 見落としを検出する仕組み
- 実証実験の測定指標

## 2. v0.3からの重要な変更

### 廃止する考え方

- `今日の目標 0 / 1 / 2 / 3件`
- 「今日のアクティブ枠は最大3件」という固定上限
- マスター項目数を少なくしてMVPを成立させる考え方
- UIに入りきる件数を先に決め、その件数へ家庭運営を合わせる考え方

### 新しい考え方

**件数はシステム都合で決めない。**

その日の家庭状態から必要なものをすべて候補化し、重要度・期限・状態・時間帯で順位を付ける。

画面上は以下の3層を基本とする。

1. `今見る` — 期限・安全・状態悪化など、今確認する価値が高いもの。件数は可変
2. `今日の候補` — 今日関係する家庭運営。件数は可変
3. `ルーティン` — 授乳、オムツ替え等の繰り返し実行。必要な場合だけ表示

「3件」は目標にも上限にも使わない。

## 3. 家庭運営マスターの目標

項目数をKPIにしない。**見落とし率を下げるために必要なだけ持つ。**

初期シードでは、おおむね150〜250責任項目を想定する。

ただし、1つの家で常時150件を表示するわけではない。

```text
全家庭向けマスター 150〜250+
        ↓ 家族構成・子の年齢・園・授乳方法・住環境
その家庭に該当 60〜120程度
        ↓ 曜日・期限・時間帯・状態・最近の実施
今日関係する候補 10〜30程度
        ↓ 緊急度・期限・状態
今見る 0〜数件
```

実際の件数は実証データから決める。

## 4. 「タスク」を2種類に分ける

### A. Routine execution

繰り返し発生する直接ケア・家事。

例:

- 授乳
- オムツ替え
- 食事を食べさせる
- 歯磨き
- 食器洗い

これらを1回ずつ「今日の目標件数」に数えない。

### B. Household responsibility / management

家庭を止めないために、誰かが気づき、判断し、閉じる必要がある責任。

例:

- オムツ在庫が次回購入まで持つか判断する
- 次の予防接種時期を把握し予約する
- 園の連絡を確認し必要物を準備する
- 洗濯物が乾燥後に放置されていないか確認し収納まで閉じる
- 明日の家族予定の衝突を解消する

本プロダクトの中心はB。

Routineは家庭状態の理解に必要な範囲だけ扱う。

## 5. 責任項目のデータ契約

各項目は最低でも以下を持つ。

| Field | 意味 |
|---|---|
| `id` | 安定ID |
| `domain` | 育児、食事、洗濯、園、医療等 |
| `label` | 利用者向けの短い名称 |
| `kind` | routine / responsibility |
| `trigger_type` | state / schedule / deadline / event / cadence / age |
| `applicability` | 家族構成・月齢・園等の条件 |
| `cadence` | daily / weekly / monthly / milestone / event / continuous |
| `priority_class` | safety / deadline / high / normal / low |
| `surface_rule` | いつ候補に出すか |
| `close_condition` | どこまでで責任が閉じるか |
| `state_inputs` | 必要な場合の状態入力 |
| `evidence_rule` | 記録から何を事実として言えるか |
| `source_class` | official / household-config / empirical |
| `source_url` | 健康・安全等で必要な一次情報 |
| `default_visibility` | 通常表示 / 折りたたみ / 設定で有効化 |

## 7. 健康・安全の扱い

健康・安全項目は「一般的にそうらしい」で実装しない。

- こども家庭庁
- 厚生労働省
- 自治体・医療機関の一次情報

を優先する。

特に次を根拠付きで管理する。

- 予防接種
- 乳幼児健診
- 安全な睡眠環境
- 窒息・誤飲
- 転落・転倒
- 水回り
- やけど
- 車・自転車移動
- 発熱・病気時の受診判断を支援する情報

アプリが診断・治療判断を代替しない。

## 8. 実証実験で測るもの

「何件完了したか」は中心KPIにしない。

### Core metrics

| Metric | 内容 |
|---|---|
| `missed_responsibility_rate` | 後から「これも必要だった」と判明した責任の割合 |
| `partner_prompt_rate` | パートナーに言われて初めて気づいた責任の割合 |
| `irrelevant_surface_rate` | 表示されたがその家庭・その日に不要だった割合 |
| `self_notice_rate` | システム提示前に利用者自身が気づいた割合 |
| `closed_loop_rate` | 実行だけで止まらず最後まで閉じた割合 |
| `management_overhead` | 記録・選択・確認に使った時間とタップ数 |
| `trust_break_count` | 間違った提案・誤った事実表示・消えない完了等の件数 |

### 実証時に毎日残す最低イベント

- surfaced
- opened
- completed
- deferred
- dismissed_as_irrelevant
- already_done
- noticed_before_surface
- partner_prompted
- missing_from_system
- close_condition_failed

## 9. 実証の成功条件

初期7日間は絶対閾値で合否を決めず、欠落とノイズを洗い出す探索期間にする。

その後の14日間では少なくとも以下を狙う。

- 同じ種類の重大な見落としが繰り返されない
- パートナーからの指示が減る方向に動く
- 不要項目の表示が減る
- 1日の管理操作が家庭運営そのものより負担にならない
- 健康・安全・期限項目で明白な誤提案がない
- 利用者が「これを見れば今日の家庭運営の全体像を把握できる」と感じる

数値閾値は探索7日間の実データから設定する。

## 10. このフェーズで作らないもの

- App Store / Google Play配信
- 本番アカウント
- クラウドDB
- 家族招待
- Push通知基盤
- 課金
- 本番分析基盤
- 高度なアニメーション

ただし、それらを後から追加できるよう責任マスターとイベント設計は安定ID前提で作る。

## 11. 次の実装順

1. `RESPONSIBILITY_MASTER_V1`を150〜250項目規模で作る
2. 各項目へ適用条件・trigger・close conditionを付ける
3. 健康・安全項目へ一次情報を付ける
4. 初期利用者の家庭条件を当て、該当項目を抽出する
5. 1日分の候補生成ロジックを作る
6. 既存PWAを「実証用の薄い表示装置」として接続する
7. 7日探索 → マスター修正 → 14日評価

**アプリUIの追加改修より先に、1〜5を完了する。**
